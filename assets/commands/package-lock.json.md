# TAGLINE

npm 生成的锁文件，固定已安装依赖树的确切版本

# TLDR

注意：**package-lock.json** 是一个生成的文件，不是可执行命令。以下命令针对它进行操作。

基于 **package.json****创建或更新**锁文件

```npm install```

**从锁文件全新安装**（若锁文件不同步则失败；用于 CI）

```npm ci```

**更新特定软件包**并重写锁文件

```npm update [package]```

对锁文件中的确切版本进行 **CVE 安全审计**

```npm audit```

在 diff 中**检查**锁文件的变更

```git diff package-lock.json```

从头**重新生成**锁文件

```rm package-lock.json && npm install```

# SYNOPSIS

**package-lock.json** - npm 依赖锁文件（放置于项目根目录）

# DESCRIPTION

**package-lock.json** 由 **npm** 自动生成，描述实际安装的精确依赖树。它记录每个解析出的版本、registry URL 和完整性哈希（SRI），因此后续安装无论清单允许怎样的 semver 范围，都会产生相同的 **node_modules**。

该文件应提交到版本控制。在 CI 中应使用 **npm ci** 而不是 **npm install**：**npm ci** 直接从锁文件安装且不会修改它，一旦它与 **package.json** 不一致就会快速失败，而且速度明显更快。

# KEY FIELDS

```json
{
  "name": "my-project",
  "lockfileVersion": 3,
  "packages": {
    "": { "dependencies": {...} },
    "node_modules/lodash": {
      "version": "4.17.21",
      "resolved": "https://registry.npmjs.org/...",
      "integrity": "sha512-..."
    }
  }
}
```

# LOCK FILE VERSIONS

```
v1 - npm 5-6
v2 - npm 7+ (backwards compatible)
v3 - npm 7+ (optimized)
```

# CAVEATS

不要手动编辑。务必提交到 git。合并冲突很常见，最好的解决办法是接受其中一侧然后重新运行 **npm install**。如果 **package-lock.json** 和 **npm-shrinkwrap.json** 同时存在，则以 shrinkwrap 文件优先。与 **npm-shrinkwrap.json** 不同，**package-lock.json** 永远不会被发布到 registry。

# HISTORY

随 **npm 5**（2017 年）引入，用于解决长期存在的可复现性问题。**lockfileVersion 2** 随 **npm 7** 发布（向后兼容 v1），**lockfileVersion 3**（npm 7+）移除了旧式的 **dependencies** 块，采用更小的纯 packages 格式。
